# User Stories

Status flow: Backlog -> Planned -> Implemented. When moving a story, keep its epic heading (create it in the target section if missing). Skill `neues-feature` moves stories through these sections.

## Priorities

Epics are worked on in four phases; acceptance criteria per epic are in `requirements.md`, "Acceptance Criteria per Epic".

1. Phase A - prove the data flow: Projektfundament und Laufzeitumgebung; Quellenadapter und Ingestion (one or two sources); Normalisierung, Deduplizierung und Clustering; Strukturierte Ereignisextraktion; Ereignisidentität und zeitliche Entwicklung.
2. Phase B - build persistent knowledge: Entitäten und Wissensmodell; Verdichtung und Daten-Lifecycle; Dashboard, Recherche und Alerts (a minimal research dashboard first); Live-Kurse und Kursdatenspeicher (as early as possible, because high-resolution price history exists only from the day collection starts).
3. Phase C - assess market impact: Markt- und Wirkungsmodell; Historische Markt- und Ereignisdaten; Prognoseprotokoll und Evaluation.
4. Phase D - operations and scaling: Skalierung und Betriebsqualität; extending sources, languages, history and models; regular evaluation and revision of the event model.

The first sprint does not build any comprehensive stock forecasting yet. It proves the whole data flow:
1. Ingest a limited selection of news sources.
2. Normalise articles and detect duplicates.
3. Create structured event candidates from articles.
4. Merge articles into events.
5. Store event changes with timestamps and source evidence.
6. Build a simple dashboard for event details.
7. Archive or delete raw data in a controlled way after successful processing.
8. Measure quality, throughput, storage needs and error rates.

5. As an admin, I want scripted database backups and a documented restore that has been tested once, so data can be recovered after a failure.

2. As an analyst, I want a uniform source adapter interface with RSS as the first adapter, storing source name, URL, publication time, fetch time and language separately, so new source types can be added without changing the event model.
3. As an analyst, I want the full text of every new article fetched from its URL - respecting robots.txt and a per-domain rate limit - and kept in a temporary raw-data layer, so the event extraction works on complete texts.
4. As an admin, I want failed fetches logged and retried with backoff, rate limits per source, and a status per source (last success, last error, consecutive failures), so temporary source outages cause no data loss.
5. As an analyst, I want a GDELT DOC 2.0 API adapter with configurable queries as the second source, so ingestion covers global events beyond the configured feeds.
6. As an admin, I want historical backfill to run separately from live ingestion, so a backfill never delays current news.
7. As an admin, I want full-text fetches that a host's bot protection blocks (e.g. the BFS article pages on www.admin.ch answer HTTP 403 to the Seismo User-Agent) recognised per source and resolved through an allowed route - a contact in the User-Agent, an official API or feed with the full text, or the publisher's permission - never by disguising the fetcher, so such sources still deliver complete texts.
8. As an analyst, I want every Quelle to carry its region - the continent it reports from, or worldwide - and the source list sortable and filterable by it, with the starter catalogue bringing the region of each source, so coverage stays balanced across continents and can be viewed per continent.
9. As an admin, I want full texts fetched only where the publisher allows text and data mining - honouring a machine-readable reservation (TDMRep: the `tdm-reservation` header or meta tag, `/.well-known/tdmrep.json`) and a list of hosts whose terms forbid it, starting with those found for the starter catalogue (BBC, France 24, The Guardian, SRF, tagesschau, SCMP, Times of India, CNBC, FreightWaves, The Loadstar, OilPrice, Rigzone, Defense News) - and otherwise keeping only the article's metadata, so articles found through GDELT respect their publishers' terms as well.
10. As an analyst, I want the ReliefWeb API as a source type, so humanitarian and conflict reports come in through the route ReliefWeb offers for automated access, since its robots.txt excludes the RSS feeds.
   - Decided (2026-10-25): the API requires an appname ReliefWeb approves by e-mail (`RELIEFWEB_APPNAME`); that approval counts as the publisher's permission, so robots.txt of api.reliefweb.int (`Disallow: /`) is not asked, the minimum interval still applies. Suchanfrage optional in ReliefWeb's query syntax; the full text comes from the report page as for any article; the publication time is `date.created`.
11. As an analyst, I want the EIA Open Data API as a source of energy data releases (e.g. the weekly petroleum and natural gas storage reports), with its API key from the environment, since EIA's robots.txt excludes its RSS feeds.
   - Decided (2026-10-25): the API returns numbers only; each of the newest 3 periods of a data set becomes one article whose text the adapter writes from them, each value with its change against the period before, stored as the raw text without a page fetch, then normalized and extracted as usual. The Quelle's URL is the API URL of a data set from EIA's API browser, without the key (`EIA_API_KEY`; a URL with `api_key` is refused). The registered key counts as EIA's permission: robots.txt of api.eia.gov (HTTP 403) is not asked. No backfill. httpx2's request log, which named every URL with its key or Suchanfrage, is off.

### Epic: Normalisierung, Deduplizierung und Clustering
1. As an analyst, I want article HTML cleaned to plain text and the metadata normalised (canonical URL, title, UTC timestamps, detected language), so all later steps work on consistent data.
2. As an analyst, I want identical articles recognised by canonical URL and content hash, so repeated fetches never create duplicate articles.
   - Note (2026-10-24): some hosts answer an error page with HTTP 200 and it is stored as the full text (the EC press corner: "temporarily unavailable" in 24 languages); such pages share a content hash and must not make different articles duplicates.
3. As an analyst, I want near-duplicate and syndicated articles linked to each other without blindly merging different events, and wrong links correctable, so the same report from several outlets is recognised and every article stays traceable to its source.

### Epic: Strukturierte Ereignisextraktion
1. As an analyst, I want a versioned event schema and an LLM extraction via Ollama - for articles that pass a configurable relevance pre-filter - that turns an article into event candidates with event type, actors, location, time, status and impacts, each statement labelled as fact, claim, forecast or interpretation and backed by a text quote, so events are structured and evidence-based.
2. As an analyst, I want the LLM output validated against the JSON schema, invalid output retried and logged, missing details marked as unknown instead of invented, separate confidence values for extraction, source quality and inference, and the model version, schema version and extraction time stored, so every extracted statement is traceable.
3. As an admin, I want the worker's stop grace period (`stop_grace_period` in `docker-compose.yml`) to be longer than the longest LLM call, so a deploy or restart lets a running extraction finish instead of killing it and repeating the call once its lease has expired.
4. As an admin, I want LLM jobs to wait while Ollama is unreachable instead of using up their attempts, so a switched-off or restarting LLM machine delays the extraction but never makes jobs fail.

### Epic: Ereignisidentität und zeitliche Entwicklung
1. As an analyst, I want each event candidate assigned to an existing event (Ereignis) or turned into a new event with a stable event ID, so several reports about the same event form one consistent event record.
   - Decided (2026-10-24): the same event is one incident with its direct continuation, not the same topic; a candidate is compared by TF-IDF cosine of its English title, summary, place and actors with the events whose reports reach to within 7 days of its own (open for 7 days after the last report, and a report found late by a backfill may precede the first by as much) - from 0.5 assigned, below 0.2 a new event, in between the LLM decides among up to 3; never to an event with a candidate of the same article; a list of events and a page per event, read-only.
2. As an analyst, I want every change to an event's state (start, update, escalation, closure, resumption) stored as a timestamped version with its source evidence, and contradicting reports kept side by side instead of merged into one fact, so the development of an event is traceable.
   - Decided (2026-10-29): a report is compared with the state in effect at its own time (publication, else fetch): the earliest known status founds the state; while ongoing an update confirms, an escalation or a closure is a new version, a start or a resumption contradicts; while closed a closure confirms, a resumption is a new version, anything else contradicts; unknown has no effect. A contradicting report changes nothing and stays visible next to the state. Versions are appended, never changed, with the time they were recorded; the existing reports are replayed by the migration in the order they were assigned.
3. As an analyst, I want to merge and split wrongly grouped events, with every merge and split recorded in an audit trail, so grouping errors can be corrected.
   - Decided (2026-10-30): merged on the event page, from its similar events (reported within 7 days, by the similarity of the assignment), into the page's event; a merged event keeps its ID and page, marked as merged into the other. A split makes the selected reports one new event, named after its earliest; the report an event is named after never leaves it. The state history of every event concerned is derived anew from its reports in the order they were assigned: versions no longer derived are marked withdrawn by the correction and stay visible, new ones are appended. Every correction records kind, time, events, the reports moved and an optional reason.
4. As an analyst, I want related events grouped into a higher-level Lage (e.g. "Krieg in der Ukraine", "Zollkonflikt USA-China", "Angriffe im Roten Meer") - proposed automatically and confirmed, merged, split or corrected by me - with one timeline across its events, their changes of state and their sources, so I can follow a development beyond single incidents and filter, watch and alert on it.
   - Decided (2026-11-03): UI term Lage. An Ereignis stays one incident (the decision of 2026-10-24); a Lage is a level above it. Proposed by the system from events over weeks - shared entities, countries, types and wording -, the LLM deciding in doubt, each proposal confirmed by the analyst. An event may belong to several Lagen (an attack in the Red Sea to "Gaza-Konflikt" and to "Störungen der Schifffahrt"). Stored in PostgreSQL; a graph database only once measurements show a need (architecture.md).
   - Decided (2026-11-03, implementing): the analyst confirms a new Lage; after that the worker adds events by itself, in effect and flagged automatic until confirmed or removed - a removed one is never added again. Names and descriptions in English like the events' titles. A Lage is open for 30 days after its latest event (Plattform-Einstellung), then dormant: an event that fits it is a proposed resumption. Once an hour, at most 20 LLM calls per hour (Plattform-Einstellung, 0 holds it). Compared by TF-IDF over words and entities; the LLM decides in doubt, scores alone only from 0.4. The event list, the start page and alert rules filter by a Lage; a watchlist can follow one. Measured on the dev data: 20 proposals in 56 s, one "Russia-Ukraine war" of 30 events after a proposal was made to see those proposed before it.

### Epic: Entitäten und Wissensmodell
1. As an analyst, I want companies, subsidiaries, persons, countries, authorities, products, commodities and sectors recognised as entities, with different name forms and identifiers resolved to one entity and uncertain matches flagged, so events are linked to the right actors.
   - Decided (2026-10-31): one LLM call per extraction recognises its reports' actors and impact targets - a kind, the usual English name, a short form, a parent, a country code, identifiers its quote states; organisation is a ninth kind (OPEC, parties, unions, armed groups); persons only in a public or business role; sectors and commodities only from a starter list the admin imports. An identifier or the same name key resolves for certain; a similar name (pg_trgm, from 0.3, only what the LLM is shown) the LLM judges the same is linked and flagged unsicher until the analyst confirms it or splits it off; else a new entity. The analyst merges similar entities on the entity page; the event page lists its entities.
2. As an analyst, I want relationships between entities (supplier, customer, competitor, regulator, commodity dependency) stored with source, validity period and quality flag, and their historical changes kept, so the knowledge model stays traceable over time.
   - Decided (2026-10-31): from reports and from the analyst. The entity recognition (schema 2) also names the relationships the reports' statements state between two names, each citing its statement, whose Beleg is the evidence; the analyst enters relationships with a source on the entity page. A supplier and its customer are one relationship. Its history are Angaben, appended and never changed; validity and review follow from them in the order they were recorded: a report that it holds opens it from its day or moves its start earlier, one that it ended closes it; the analyst sets dates and review. The quality flag is the analyst's review: Ungeprüft, Bestätigt, Bestritten (kept, not in effect). Merges and splits of entities carry the Angaben along.

### Epic: Verdichtung und Daten-Lifecycle
1. As an admin, I want raw article texts deleted according to their source's retention period, but only after processing and validation have succeeded, so storage stays bounded while events, evidence quotes and source references remain understandable and verifiable.
   - Decided (2026-10-31): processing ends with the article's current extraction, for a duplicate with its normalization, for any other article once the extraction can take it no more (its maximum age); the retention period of its Quelle counts from then, for a deleted Quelle the default 30 days. A failed processing - an unreadable text, only unusable answers of the model - keeps the raw text until a retry succeeds. The answer and its plain text go together (the plain text is the full text too), so an article can be extracted again only within its retention period; metadata, hash, fingerprint and quotes stay. The worker deletes once an hour; the article page says when, the Datenbestand page where the raw texts stand.
2. As an admin, I want storage usage monitored and selected articles reprocessed after a schema or model change, so the knowledge base can evolve without re-running the whole history.
   - Decided (2026-10-31): both steps - the event extraction and the entity recognition - run again, chosen by their Stand (the step's current runs by schema version and model), optionally of one Quelle and a period, as a Neuverarbeitung on the new page Datenbestand: one at a time, behind live work, at most a number per hour of its own (Plattform-Einstellung); an article's page reprocesses its own at once. A new extraction replaces the article's reading: its reports are assigned as usual and find their events through the old reports, which then leave them as a Korrektur "Neuverarbeitung"; the old reading, its versions and its Angaben stay, marked, no longer counting. A recognition run again replaces its mentions. Storage: the state now (database, largest tables, raw texts per Quelle, backups, free space) and a measurement once a day with the growth per day over 7 and 30 days.

Relevance is the breadth of the coverage - at least 2, 3 or 5 sources - and an economic impact a report names (on a company, sector, commodity or market). Country and type match the event or one of its reports; sector and company an entity its reports name (a company by a part of a name form); horizon an impact a report names. The list adds a period with new, developing or a change of state within it; the start page keeps its own period, its links keep the filter. 3. As an analyst, I want watchlists and configurable, throttled rule-based alerts, so I learn about relevant new events and material changes without checking manually.

An Alert-Regel covers its watchlist's events that match the event list's filter and reports, while active, a new event (also one that reaches the relevance asked for later), a change of state (as the start page counts it) and, if chosen, every new report. Throttled: an event's hits go out as one alert, the same event again only after a quiet period (6 h by default) unless its state changed, at most a number per hour (5 by default), the rest as one Sammel-Alert once the hour allows; nothing is dropped. 4. As an analyst, I want historical search and similar past events, with uncertainty and contradicting evidence shown instead of hidden behind a single score, so I can put current events into context.

Every listed event shows its statements by kind, its contradictions and how many of each level are low or unknown; the event page adds Unsicherheit und Widersprüche - the statements by kind, the three levels as counts each, the reports the LLM assigned, the reports contradicting the state at their time, the impacts on one target two reports see in opposite directions (by its entity, else its name; one report seeing both ways is none, seen on the dev data) and the uncertain name forms - and Vergleichbare frühere Ereignisse: other incidents whose last report came before its first, of its type or naming most of its entities, by TF-IDF over words and entities as the Lagen, from 0.10, at most 10, each with its reasons (similarity, type, country, shared entities) and how it went on (state, escalated, closed since, duration), counted as closed, ongoing and escalated - numbers, not a probability. Market reactions follow with the event-study story. No new field.

### Epic: Live-Kurse und Kursdatenspeicher

The worker fetches every active Wertpapier once a minute and keeps each price as received, each once. Wertpapiere are entered by the admin or imported with a starter list of indices and broad ETFs; linked to an entity by ISIN or by choice; the entity's and the event's pages show their latest prices.
   - Changed (2026-10-31, with Historische Markt- und Ereignisdaten, story 1): the source must be free and never throttled, delayed is fine, for personal use. Live prices now come per Wertpapier from its own source - SIX for Swiss ones (15 minutes delayed, no key), Alpaca for US ones (real time from IEX, free account), EODHD only optionally - at an interval of the Plattform-Einstellungen (30 minutes by default) instead of every minute; a Wertpapier has a Live-Kurs or not (UI: Live-Kurs an / aus). The starter list holds Swiss indices and an ETF from SIX and broad US ETFs from Alpaca's list.
2. As an admin, I want to mark Wertpapiere as tracked (verfolgt) so their prices (Kurspunkte) are collected continuously at the highest resolution the source offers and kept at full resolution for a configurable retention period (Plattform-Einstellung; at least 3 months by default, longer or unlimited when the measured storage need allows it) before being compressed into coarser intervals instead of deleted, so I have high-resolution price history for later event studies.
   - Decided (2026-11-04): the highest resolution free of each source: Alpaca's minutes of all US exchanges (SIP, OHLC and volume, free once 15 minutes old), asked every 15 minutes from where the collection came, so an outage is fetched afterwards; SIX's and EODHD's latest price every minute. A time without a collection during trading hours (SIX weekdays 9:00-17:30 Zurich, EODHD every hour) longer than three minutes is an Erfassungslücke with its cause, recorded in a table of its own, never filled. After the full-resolution period (Plattform-Einstellung, 90 days, 0 unlimited) the points become hours - OHLC, volume summed for minutes and unknown for quotes, received when the last of them was - deleted and inserted in one statement. Tracking is a bulk action on the Wertpapiere list and a button on the page, at most 50 (Plattform-Einstellung); a tracked SIX or EODHD Wertpapier needs no separate Live-Kurs fetch. The Datenbestand page shows the measured need per tracked Wertpapier and day once a day is measured. Verified against the real sources on a copy of the dev data: SIX's quote 15 minutes delayed, 123 SIP minutes of Apple's pre-market, a 10-minute gap recorded as not asked.
   - Added (2026-11-04): switched on, a US Wertpapier's SIP minutes of the days before are fetched afterwards (Plattform-Einstellung, 90 days, 0 none), behind live work, a week per step, those switched on together in one request, up to 16 minutes ago only. Verified against Alpaca: 3 days of Apple and SPY, about 2000 minutes each, in two requests.

### Epic: Historische Markt- und Ereignisdaten
1. As an analyst, I want licensed historical price, volume, benchmark and company data in a point-in-time model that handles splits, dividends, delistings and identity changes, so an analysis can reconstruct what was known on a given date and later information never leaks into earlier forecasts.
   - Decided (2026-10-31): Alpaca's free market data - every US stock and ETF, traded ones and those no longer traded, so all of them can be compared with events, not only those with a Live-Kurs. Daily prices of all US exchanges, unadjusted, back to 1 January of the first year of a Plattform-Einstellung (2 years by default; 11 on dev, from 2016 on); corporate actions (splits, dividends, changes of symbol, mergers, worthless removals) kept apart; the exchanges' calendar. Benchmarks are the broad ETFs (SPY, QQQ, DIA, VTI, ...) - no free source has the indices' history. Company data is identity only: name, exchange, symbol now and its changes, delisting, and the Entität by ISIN (from the CUSIP), ticker or name - the last uncertain. Point in time: a day's prices count as known from its close, a corporate action from the day it was processed; adjustment is computed for a moment, never stored. Swiss Wertpapiere have live prices only (SIX), no history yet. Found against the real API (2026-10-31): Alpaca's list sends no CUSIP - a Wertpapier takes it from its recent corporate actions, so linking by ISIN follows those - and holds only part of the Wertpapiere no longer traded (e.g. not Twitter); the history of one it lacks comes only under its successor's symbol where Alpaca maps a rename.
2. As an analyst, I want event-study windows for different horizons and separate training, validation and test periods, with data gaps and adjustments documented, so market reactions to events can be measured against a market or sector benchmark.
   - Decided (2026-11-04): computed whenever a page asks, nothing stored. Of each event the US Wertpapiere (Alpaca's, with daily prices) of the entities its reports name, traded or no longer, against SPY and the ETF of the sector of the starter list its reports name most (fixed in code: XLE for Öl und Gas, ...; none named: the market only); SPY and the sector ETFs are fetched first in the daily sync. Ereignistag: the first trading day closing after the first report. Windows of trading days: Vorlauf (-5 to -1), the Ereignistag, up to +1, +5, +20, +60, each from the close before; returns with dividends, split-adjusted. Two measures side by side: return minus the benchmark's, and the market model's abnormal return (alpha and beta from days -130 to -11, at least 60, else too little data) with its t value.
